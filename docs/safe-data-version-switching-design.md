# Safe data version switching design

## Status and scope

> Status: DESIGN ONLY. This document specifies a proposed source-version switch against an unchanged original physical project root. Implementation and operations on an existing installation require separate owner authorization. It does not close WP-06 or G6.

This is a design record for WP-06, not an implemented capability. It adds no
code, command, workflow, selector, updater, or executable switch mechanism,
and it performs no operation on any installation. Phase 1 boundaries are
retained exactly: `paper_only=True`, `report_only=True`, and `readonly=True`
where those flags exist, with project-private native PostgreSQL as the only
approved durable persistence target for project data. Nothing in this design
authorizes live execution, account authentication, private-key handling, or
order placement.

## Problem statement

A version change is not one operation. At least four distinct operations are
involved, and keeping them separate is the main purpose of this design:

1. **Installing a newer distribution kit**: verifying and extracting a new
   immutable kit, with its own manifest, runtime, and source tree, into its own
   new directory. Installation changes what exists on disk; it changes no
   database.
2. **Selecting newer Python source**: invoking entrypoint scripts from the new
   kit. Each invoked script selects its own adjacent source tree for that
   process. Source selection changes which code interprets the project; it
   changes no database.
3. **Adopting a newer migration catalog**: extending, under separate review,
   the effective migration catalog recognized at the data root, subject to
   append-only validation and hash checks. A catalog change changes what
   schema is considered current; it applies nothing to a live cluster by
   itself and is never performed implicitly by new source.
4. **Migrating a database**: applying DDL to the cluster under the existing
   transactional PostgreSQL ledger, recording ledger identity and effective
   hashes. Migration changes stored schema and remains explicit, append-only,
   and separately gated.

The design goal is narrow: switch the selected source version and its
environment while keeping `--root` pointed at the original physical project
root, preserving the existing installation state completely, and treating any
schema, catalog, runtime, identity, or business-data change as a separately
designed and separately authorized operation.

Conflating these operations is the primary hazard this design guards against:
overlaying a new kit onto a retained old kit destroys the rollback baseline
and breaks kit verification; assuming that new source creates missing tables
because its checkout contains newer migrations is explicitly false; treating
backup/restore as an upgrade or rollback tool misuses a disaster-recovery
operation with an absent-target requirement; and describing a managed read as
byte-preserving overstates what a session guarantees once the engine starts.

## State that must be preserved

A source-version switch must preserve, without modification:

- **The whole PostgreSQL cluster and its WAL and control state** under the
  original root, including any retained unclean-shutdown markers. Preservation
  of physical bytes is claimed only while the engine remains stopped.
- **Research records and their original timestamps**, including the server
  receipt timestamps that settlement and evaluation checks rely on.
- **Failed and incomplete claims**: interrupted attempts, saved rejections,
  unscored and excluded history. Incomplete claims can still block strict
  evaluation; they must not be deleted, replayed, or reclassified to make an
  installation appear clean.
- **Migration ledger identity and effective hashes**: the transactional
  PostgreSQL ledger and the checked-in hash manifest
  (`database/migrations.lock.json`) over `supabase/migrations` keep their
  identity, and the applied-schema history remains exactly what it was.
- **Instance/system identity and physical-root binding**: the recorded
  instance identity and system identity, and their binding to the original
  physical project path, remain stable.
- **Runtime version and inventory**: the `runtime/postgres` engine version and
  engine file inventory are unchanged by a source selection.
- **Generated owner/application credentials and existing permissions**: these
  are inventoried by description of posture only. Secret values are never
  printed, inspected, copied, or regenerated by this design. Cold-backup
  archives contain credentials and remain private under their existing
  protection requirements.
- **The retained old kit, source revision, and environment**: the complete
  old directory, its pinned source revision, and its Python environment stay
  in place as the rollback baseline.

The original root supplies `.local/postgres` (the private cluster with
OS-protected configuration and credentials), `runtime/postgres`,
`database/migrations.lock.json`, and `supabase/migrations`. Its physical
identity must remain stable: the initialized root is not renamed, moved, or
relocated by a version switch.

## Existing components and compatibility limits

This design deliberately reuses the existing entrypoints, `ProjectPostgres`,
distribution verification, migration catalog and ledger checks, and the
cold-backup functions. Their current contracts impose these limits:

- `--root` selects **data, runtime, private configuration, and the migration
  catalog**, not the version of Python source. The invoked script selects its
  own adjacent source tree
  ([quickstart: select one code version and one physical project](../database/quickstart.md)).
- `start_project.py` has no `--root` option and can initialize its own
  installation. It is **not** the entrypoint for selecting new code against an
  old database.
- Managed session admission (`ProjectPostgres.session()` through
  `_verify_session_bundles` in
  [server.py](../src/polymarket_alpha_lab/project_postgres/server.py)) checks
  both the source kit and the selected data-root kit when either distribution
  marker exists. Valid hashes establish byte integrity, **not** cross-version
  schema compatibility; pending migrations at the data root still block the
  session.
- New source cannot obtain missing tables merely because its own checkout
  contains newer migrations
  ([quickstart: preserving data while selecting another version](../database/quickstart.md)).
- The existing `backup`, `verify-backup`, and `restore` operations remain
  bound to their current contracts
  ([database/README.md: private cold backups and absent-target recovery](../database/README.md)).
  `--allow-catalog-extension` accepts a validated historical catalog prefix of
  the current effective migration catalog for backup verification and
  restore; it neither checks the live ledger nor applies migrations.
- Restore requires an **absent** target at the original physical root and is a
  separate disaster-recovery operation, not an upgrade, a rollback, or a move
  tool.

## Proposed operator procedure

The following is a future, release-specific procedure. It requires explicit
owner authorization before any step runs on an existing installation, and it
assumes the exact version pair, dependencies, and compatibility evidence have
been pinned for that release. This design adds no executable switch
mechanism; every step uses existing, reviewed tooling only.

1. Pin the old and candidate source commits and trees, trusted outer kit
   hashes, environments, the original physical root, the original runtime,
   and the exact applied-schema compatibility requirements.
2. Verify and extract the candidate kit into a new side-by-side directory.
   Preserve the complete old kit and the original database root. Preparing
   candidate source does not mean initializing a replacement database.
3. Review candidate code against the original root's actual catalog and
   schema contract. Refuse pending migrations, an incompatible schema, a
   changed runtime or identity, or either kit failing integrity checks.
4. Under the later approved maintenance procedure, stop new task admissions
   and let admitted work drain through the existing lifecycle and stop
   controls. Preserve original claims and failures. Do not force-kill,
   delete locks, or replay tasks to make the installation appear clean.
5. After draining and stopping the engine, create and verify a private cold
   backup through the existing tooling. Keep it outside the project under its
   existing protection requirements, with an independently retained
   checksum. It contains credentials and must not be published.
6. Require an explicit operator-approved switch point binding the reviewed
   candidate, the old version, the original root, the compatibility evidence,
   and the recovery material.
7. Change the selected source/environment invocation while keeping `--root`
   pointed at the original physical project root. The switch makes no
   business-record, schema, catalog, runtime, identity, or credential
   changes.
8. Treat any subsequent engine-start or managed-read acceptance as a
   separately authorized operation.

A precise physical-write distinction applies throughout. A stopped
source-selection check can preserve the original database bytes, but
`ProjectPostgres.session()` may start PostgreSQL and update logs, control, and
WAL state even when the business operation is read-only. **Byte-identical
cluster files must not be promised after starting the engine.** Stopped
runtime verification also invokes the approved native version and control
binaries (version probes over programs such as `postgres`, `pg_ctl`, and
`pg_controldata`); "offline" must not be described as "no executable
invocation."

## Rollback and failure handling

Routine rollback means selecting the retained old kit, source, and
environment again, still targeting the same original physical root. This is
valid only while the original schema and storage contract remain compatible.

Rollback of source selection does not undo newly written records, migrate
schema backward, replace the runtime, or restore a backup over an existing
cluster. Any requirement for such an operation stops the procedure for a
separate design and authorization.

Never overlay an old kit with new files, modify its manifest
(`PROJECT-BUNDLE.json`), copy `.local` as a form of migration, relocate the
initialized root, or delete a working database to satisfy restore's
absent-target check.

## Evidence required for later acceptance

- **Design evidence**: this document, its source references, and
  documentation review.
- **Offline compatibility evidence**: the exact release pair, dependencies,
  catalog and schema assumptions, and command/root selection.
- **Isolated native Windows evidence**: synthetic same-root source selection
  and rollback, lifecycle and ownership behavior, rejection paths, and
  preservation checks on disposable data.
- **Operator-reported evidence**: clearly labeled reports, retaining first
  failures and reruns separately.
- **Owner-authorized installation acceptance**: later evidence for the exact
  installation and approved operations.

None of these substitutes for G1-G6 completion, real-model acceptance, or
statistical strategy validation.

## Non-goals and owner authorizations

Non-goals: cross-machine or cross-path migration; automatic transformations,
upgrades, or instance imports; Docker or Supabase services; external or
shared databases; copying `.local` as migration; new selectors, updaters, or
switch tooling; and live execution of any kind.

Future approvals still required, each explicit and separate: implementation of
this design; the exact version pair and root; backup and engine operations;
the switch and rollback window; and any separately proposed schema, runtime,
or data migration. The existing D1-D3 owner decisions are not reopened by
this document.
